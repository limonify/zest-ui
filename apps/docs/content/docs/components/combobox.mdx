title: Combobox
description: A text input that filters a list of items, with single or multiple selection.

`Combobox` is a text input paired with a filtered list. Typing filters the items; choosing one
fills the input and closes the list. Set `multiple` to select several, shown as chips. For
free-text suggestions without a bound value, use
[`Autocomplete`](/docs/components/autocomplete), which reuses every combobox part.

## Usage

Press it, then read it. The behaviour is headless — the **Code** tab is the component; the **StyleSheet** and **Uniwind** tabs are two ways to design it.

`Combobox.Chips` and its children are only for `multiple`; a single-selection combobox is just
`Combobox.Input` and the portal. `Combobox.Group`/`Collection` are only for grouped `items` — a
flat list renders items straight from `Combobox.List`.

## A button instead of a text field

`Combobox.Input` makes the closed state a text field. On a phone that often reads wrong — a bare
input gives no hint that a list will appear. `Combobox.Trigger` makes it a button instead, and the
input moves *inside* the popup where it filters:

```tsx
<Combobox.Root items={COUNTRIES} value={value} onValueChange={setValue}>
  <Combobox.Trigger style={styles.trigger}>
    <Combobox.Value />
  </Combobox.Trigger>

  <Combobox.Portal>
    <Combobox.Backdrop style={styles.transparent} />
    <Combobox.Positioner>
      <Combobox.Popup style={styles.popup}>
        <Combobox.Input placeholder="Search" style={styles.input} />
        <Combobox.List>{/* … */}</Combobox.List>
      </Combobox.Popup>
    </Combobox.Positioner>
  </Combobox.Portal>
</Combobox.Root>
```

The trigger is `role="combobox"` with `aria-haspopup="listbox"` and reports `state.open`.
`Autocomplete.Trigger` is the same part, re-exported.

The popup anchors to `Combobox.Trigger` whenever there is one, and to `Combobox.Input` otherwise —
it has to be that way round, because in this shape the input is *inside* the popup and anchoring to
it would position the popup against itself. `state.triggerWidth` follows the same rule, so it is
always the width of the control the user pressed.

Two things are worth knowing about the popup's height in this shape. React Native does not clip a
child to its parent's bounds, so a `maxHeight` popup needs `overflow: 'hidden'`; and once it is
clipped, the rows have to scroll — `Combobox.List` is headless, so that is a `ScrollView` (or a
`FlatList`, see [Long lists](#long-lists)) you supply:

```tsx
<Combobox.Popup style={{ maxHeight: 240, overflow: 'hidden' }}>
  <Combobox.Input placeholder="Search" />
  <Combobox.List render={(props) => <ScrollView {...props} />}>{/* … */}</Combobox.List>
</Combobox.Popup>
```

## Grouping items

An entry in `items` becomes a group when it carries its own `items`. Filtering then runs **inside**
each group, and a group whose items all filtered out is dropped — so a group never renders empty.
A group is never matched on its own label: a query that happens to spell "Fruit" should not
resurrect everything under it.

`Combobox.List` hands you each surviving entry; `isComboboxGroup` tells the two apart.

```tsx
import { Combobox, isComboboxGroup } from '@limonify/zest-ui';

<Combobox.Root items={[
  { label: 'Fruit', items: ['Apple', 'Apricot'] },
  { label: 'Vegetable', items: ['Carrot'] },
]}>
  {/* … */}
  <Combobox.List>
    {(entry) =>
      isComboboxGroup(entry) ? (
        <Combobox.Group key={String(entry.value)} items={entry.items}>
          <Combobox.GroupLabel style={styles.groupLabel}>{entry.label}</Combobox.GroupLabel>
          <Combobox.Collection>
            {(item) => (
              <Combobox.Item key={String(item.value)} item={item} style={styles.item}>
                <Text>{item.label}</Text>
                <Combobox.ItemIndicator><Text>✓</Text></Combobox.ItemIndicator>
              </Combobox.Item>
            )}
          </Combobox.Collection>
        </Combobox.Group>
      ) : null
    }
  </Combobox.List>
</Combobox.Root>
```

A group's `value` defaults to its label and is only ever an identity — groups are not selectable,
and selection is always resolved against the flat list of items.

Used outside a group, `Combobox.Collection` renders every filtered item with groups flattened away.

`Combobox.ItemIndicator` renders only while its item is selected; `keepMounted` keeps it mounted so
you can hide it with a style instead, which is what an exit animation needs.

## Long lists

`Combobox.List` mounts a row for every filtered entry. That is the right default — most lists are
short, and virtualizing one costs you `getItemLayout`, key management and a scroll container you
did not ask for. Past a few hundred rows it stops being right.

zest has no `virtualized` prop: upstream's is built on DOM measurement, and React Native already
ships the answer in `FlatList`. What zest owes you is the filtered data, which is on
`state.items` — so swap the element and hand it over:

```tsx
import { FlatList, Text } from 'react-native';

<Combobox.List
  render={(props, state) => (
    <FlatList
      {...props}
      children={undefined}
      data={state.items}
      keyExtractor={(item) => String(item.value)}
      renderItem={({ item }) => (
        <Combobox.Item item={item} style={styles.item}>
          <Text>{item.label}</Text>
        </Combobox.Item>
      )}
    />
  )}
/>
```

Two details make it work:

- **Drop `children`.** `FlatList` takes its rows from `data`; the mapped children zest would
  otherwise pass are ignored, and passing them wastes the work of building them. Omitting the
  `children` prop on `Combobox.List` skips that mapping entirely.
- **`state.items` is the filtered list**, the same entries `children` would have received, in the
  same order. It re-narrows as the query does, so `FlatList` re-renders from it for free.

With grouped `items` the entries are groups, so either flatten them yourself for a `SectionList` or
keep `Combobox.List`'s children form — grouping and virtualization do not compose on their own.

`Select.List` needs nothing equivalent: its rows are your own JSX, so use a `FlatList` inside
`Select.Popup` directly, or swap `Select.List`'s element the same way.

## Announcing results

Filtering never moves focus, so a screen reader is not told that the list behind the input just
changed. `Combobox.Status` is a polite live region that says how many items are left:

```tsx
<Combobox.Status>{(state) => (state.count === 0 ? 'Sonuç yok' : `${state.count} sonuç`)}</Combobox.Status>
```

Without a function child it announces an English count. It renders nothing while the list is
closed, and it counts items inside groups rather than the groups.

React Native's `accessibilityLiveRegion` is Android-only, so on iOS the same text is spoken through
`AccessibilityInfo.announceForAccessibility` instead — announcing on both would say it twice on
Android. Either way it only speaks when the text actually changes, so a keystroke that does not
change the count stays quiet.

## Multiple selection

With `multiple`, the value is an array and pressing an item toggles it instead of replacing the
selection. The list **stays open** so the next pick costs nothing, and the input is left to the
query — it is never filled with a selected label. The one exception is a list you have filtered:
selecting there ends that query, so the list closes and the input clears with the `input-clear`
reason.

Render the selection with `Combobox.Chips`. `Combobox.Value` hands the selected items to a function
child and then renders no element of its own, which is what keeps chips out of a `Text`:

```tsx
<Combobox.Root items={LANGUAGES} multiple value={value} onValueChange={setValue}>
  <Combobox.Chips style={styles.chips}>
    <Combobox.Value>
      {(items) =>
        items.map((item) => (
          <Combobox.Chip key={String(item.value)} style={styles.chip}>
            <Text>{item.label}</Text>
            <Combobox.ChipRemove accessibilityLabel={`Remove ${item.label}`}>
              <Text>×</Text>
            </Combobox.ChipRemove>
          </Combobox.Chip>
        ))
      }
    </Combobox.Value>
    <Combobox.Input placeholder="Add a language" style={styles.chipsInput} />
  </Combobox.Chips>
  {/* the portal, exactly as above */}
</Combobox.Root>
```

A chip is removed by its **position** in the selection, so render chips in the order
`Combobox.Value` gives them — mapping over that array does it for you.

`Combobox.Clear` empties the selection and the input together. It renders nothing while there is
nothing to clear; pass `keepMounted` to hide it with a style instead, which is what an exit
animation needs. It works in a single-selection combobox too, and in an `Autocomplete` it clears
the input text.

```tsx
<Combobox.Clear accessibilityLabel="Clear" style={styles.clear}>
  <Text>✕</Text>
</Combobox.Clear>
```

Neither `Combobox.ChipRemove` nor `Combobox.Clear` returns focus to the input, unlike the web
version: with `openOnFocus` that would reopen the list, which is not what removing a chip asks for.
Upstream's arrow-key navigation between chips is not ported either — there is no Tab key on mobile.

### Cancelling a change

Every callback receives an event details object alongside the new value. Calling `cancel()` on it
vetoes the change — and because one object is shared across a single interaction, cancelling in
`onValueChange` also stops the list from closing:

```tsx
<Combobox.Root
  onOpenChange={(open, eventDetails) => {
    if (!open && eventDetails.reason === 'outside-press') {
      eventDetails.cancel();
    }
  }}
/>
```

The reasons a combobox reports are `input-press`, `input-change`, `input-clear`, `trigger-focus`,
`item-press`, `chip-remove-press`, `clear-press`, `outside-press`, `escape-key`,
`imperative-action` and `none`.

### Opening it from elsewhere

`Combobox.createHandle()` connects a root to an input rendered outside it, and lets you open and
close the list imperatively:

```tsx
const handle = Combobox.createHandle();

<Combobox.Input nativeID="fruit" handle={handle} />
// …anywhere else in the tree
<Combobox.Root handle={handle}>{/* … */}</Combobox.Root>

handle.open('fruit');
handle.close();
```

`actionsRef` is the other half of that: `actionsRef.current.close()` closes with the
`imperative-action` reason, and `unmount()` closes *without* firing `onOpenChange` — which is what
you call once your own closing animation has finished.

### Sizing the popup to its trigger

The positioner and the popup both publish `triggerWidth` and `triggerHeight` — the measured size of
whatever the popup is anchored to, and the React Native counterpart of the web's `--anchor-width`
CSS variable:

```tsx
<Combobox.Popup style={(state) => [styles.popup, { minWidth: state.triggerWidth }]} />
```

That is `Combobox.Trigger` when there is one and `Combobox.Input` otherwise, matching what the
popup is positioned against. Both are `undefined` until the anchor has been laid out once.

## Animation

`Combobox.Popup` publishes `state.transitionStatus`. Keep the portal mounted with `<Portal keepMounted>` and fade the list in and out:

```tsx
import Animated, { FadeIn, FadeOut } from 'react-native-reanimated';
import { Combobox } from '@limonify/zest-ui';

<Combobox.Popup render={(props) => (
  <Animated.View {...props} entering={FadeIn.duration(120)} exiting={FadeOut.duration(120)} />
)}>
  {/* ... */}
</Combobox.Popup>
```

See the [Reanimated guide](/docs/guides/animation-reanimated) for the full contract.

## Inside a Field

A combobox reports itself to a surrounding [`Field.Root`](/docs/components/field) the same way a
`Select` does: the input is named by `Field.Label` and described by `Field.Description`/`Error`, it
inherits the field's `disabled`, and choosing a value runs the field's `validate`. Closing the list
is a combobox's blur, which is when `validationMode="onBlur"` fires.

```tsx
<Field.Root name="country" validate={(value) => (value ? null : 'Pick a country')}>
  <Field.Label>Country</Field.Label>
  <Combobox.Root items={COUNTRIES} value={value} onValueChange={setValue}>
    <Combobox.Input />
    {/* … */}
  </Combobox.Root>
  <Field.Error />
</Field.Root>
```

That is also what lets it take part in a [`Form`](/docs/components/form): submitting validates the
combobox along with everything else, and focuses its input when it is the first field that failed.

## Accessibility

The input is `accessibilityRole="search"` with `aria-expanded` and `aria-autocomplete="list"`; each
item is `role="option"` with `aria-selected`. In `multiple` mode the popup adds
`aria-multiselectable`, and `Combobox.Chips` becomes a `role="toolbar"` once it holds chips.

`Combobox.ChipRemove` and `Combobox.Clear` have no label of their own — give them one:

```tsx
<Combobox.ChipRemove accessibilityLabel={`Remove ${item.label}`} />
<Combobox.Clear accessibilityLabel="Clear selection" />
```

### Placeholders and disabled items

`Combobox.Value` takes a `placeholder` shown while the input is empty, and reports
`state.placeholder` so it can be styled differently. `Combobox.Item` takes `disabled` — a disabled
item ignores presses and reports itself to assistive technology; a disabled `Combobox.Root` disables
all of them.

```tsx
<Combobox.Value placeholder="No country yet" />

<Combobox.Item item={item} disabled={item.value === 'antarctica'} />
```

### Object values

Values are compared with `Object.is`, so an object value only ever matches itself. If `items` is
rebuilt on every render — a plain inline array is — the selection is dropped the moment the
identity changes. `isItemEqualToValue` is how you match by content instead:

```tsx
<Combobox.Root
  items={people}
  value={selected}
  onValueChange={setSelected}
  isItemEqualToValue={(item, value) => item.id === value.id}
/>
```

It applies everywhere the selection is compared: which item is marked selected, the label filled
into the input, which chips render, and what a `multiple` press toggles. `null` and `undefined`
never reach your comparer, so it does not have to guard against an empty selection.

Writing it inline costs nothing: items subscribe to whether *they* are selected, not to the
comparer, so one whose identity changed but whose answer did not re-renders nothing.
